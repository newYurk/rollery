# ADR-001 — Core V2: границы модели и инварианты

- **Статус:** proposed
- **Дата:** 2026-09-03
- **Область:** `play/core-v2/`; новый геометрический kernel.
- **Не изменяет:** текущий `play/model/`, UI, рендер, каталог, `sim/` и архивные рецепты.

## Контекст

Текущий forward-путь смешивает геометрию листа, правила режимов, глобальное состояние и отрисовочные допущения. В кольцевой кинематике обнаружено нарушение сохранения длины: один участок листа может получить разные длины дуги в слоях риса и нори; часть координат выходит за физическую длину листа (issue #165). Пазл отдельно выводит длину листа из `turns`, поэтому не использует ту же физику, что базовый режим (issues #83, #85).

V2 не является переписыванием приложения. Это новый маленький, чистый forward-kernel, который должен сначала доказать корректность на ограниченном классе роллов, а затем подключаться через адаптер.

## Решение

Создаётся независимый модуль `play/core-v2/`. Он принимает сериализуемый рецепт в миллиметрах и возвращает состояние намотки, срез, измерения и диагностики. Core V2 не читает DOM, URL, canvas, глобальный `S`, FPS или режим UI.

```text
Recipe + Base + HandProfile
  → validateRecipe
  → buildWinding
  → sampleSection
  → measurements + diagnostics
```

### V2 моделирует

- Цилиндрические маки из одного листа.
- Хосомаки и футомаки как первые базовые fixtures.
- Один поперечный срез по заданной координате `vSliceMm`.
- Нори и рисовую постель с заданным профилем толщины.
- Размещения ингредиентов в физических координатах листа.
- Детерминированный режим `neutralHand`.
- Явно определённый шов и окно допустимого размещения начинки.

### V2 пока не моделирует

- Тэмаки, поскольку это конус, а не цилиндр.
- Урамаки: это отдельная топология слоёв, не числовой preset.
- Физически достоверные квадратные и треугольные сечения.
- Реальную деформацию, разрушение, скольжение и стохастический результат руки.
- Мини-роллы, кадзари-маки, второй лист, сращивание листов и вложенную скрутку.
- Мазки как первичную доменную сущность. До отдельного ADR мазок компилируется в `Patch[]` до входа в kernel.
- Inverse design. Он не начинается, пока forward-kernel не прошёл fixtures.

## Контракт рецепта

```ts
type RecipeV2 = {
  version: 2
  baseId: string
  sheet: { lengthMm: number; widthMm: number }
  wrap: { materialId: string }
  rice: { profileId: string }
  patches: Patch[]
  hand: NeutralHand | RecordedHand
}

type Patch = {
  id: string
  materialId: string
  uMm: number
  vMm: number
  widthMm: number
  lengthMm: number
  heightMm: number
  rotationDeg: number
  placement: 'embedded' | 'surface' | 'stacked'
}

type NeutralHand = { mode: 'neutral'; seed: 0 }
type RecordedHand = { mode: 'recorded'; seed: number; press: number; speed: number; wobble: number }
```

Для puzzle mode разрешён только `NeutralHand`. Одинаковые `RecipeV2` и версия kernel обязаны выдавать одинаковые measurements и одинаковую карту материалов. Режим с рукой использует только полностью записанный профиль руки; неявная случайность запрещена.

## Инварианты

1. **Единая длина листа.** У листа одна физическая длина `L`. Любой его участок `[u0, u1]` имеет одну длину независимо от материала, слоя и способа выборки.
2. **Полнота координат.** Каждая точка намотки отображается в `uMm ∈ [0, L]`. Нет фантомного участка за концом листа и нет потерянного участка внутри него.
3. **Параметризация по дуге.** Связь `uMm → sMm → θ` строится через накопленную длину дуги, а не пропорцией номера бина. В допустимой области она обратима с численно заданной погрешностью.
4. **Явный шов.** Шов имеет конкретный диапазон координат листа и положение в ролле. Он не выводится косвенно из числа витков.
5. **Ограниченная область применимости.** Если раскладка не помещается в closure window, kernel возвращает `invalid` или `outsideModelScope`; он не рисует идеальный ролл без диагностики.
6. **Единая физика режима.** Puzzle не может удлинять лист ради `turns`. Число витков — измеренный результат длины листа, толщины и намотки, а не независимый вход puzzle-уровня.
7. **Семантическая честность формы.** Пока квадрат/треугольник не влияют на доменную геометрию, они не могут быть условием puzzle-уровня, целевой метрикой или физическим утверждением.
8. **Чистота.** Kernel не меняет входной рецепт и не читает неявное глобальное состояние.

## Поведение вне модели

| Случай | Обязательный результат |
|---|---|
| Координата патча за пределами листа | `invalid: patch_out_of_sheet` |
| Группа вне closure window | `outsideModelScope: closure_window` |
| Тэмаки | `unsupported: conical_roll` |
| Урамаки до отдельной топологии | `unsupported: inside_wrap_topology` |
| Нефиксированный hand в puzzle | `invalid: non_neutral_hand_in_puzzle` |
| Запрошенная физическая форма, которой kernel не моделирует | `unsupported: section_shape` |

Никакой из этих случаев не должен silently fallback к другому виду ролла или к визуально аккуратному, но семантически неверному срезу.

## Первые fixtures

1. Пустой хосомаки: все координаты листа покрыты ровно один раз, шов определён, фантомной длины нет.
2. Хосомаки с одним огурцом в центре closure window: центр, площадь и слой ингредиента воспроизводимы.
3. Тот же ингредиент у границы closure window: результат либо меняется непрерывно, либо возникает явная диагностика до разрыва.
4. Ингредиент за границей closure window: срез не выдаётся как валидный.
5. Футомаки с рядом ингредиентов: длина листа, шов и материал на лучах не зависят от порядка вычисления.
6. Повторный запуск каждого fixture: совпадают hash рецепта, hash wind-state, measurements и material map.

Для каждого fixture измеряются как минимум: использованная длина листа, непокрытая/фантомная длина, диапазон `uMm`, положение шва, число пересечений обёртки по лучам, диаметр, площадь и центр каждого видимого ингредиента, hash результата.

## План миграции

1. Зафиксировать legacy как read-only oracle; не переписывать UI и рендер.
2. Реализовать V2 для fixture №1 и №2 без подключения к приложению.
3. Добавить mutation tests: намеренно сломанная длина, выход `u` за лист, зависимость от порядка патчей и неявный random обязаны красить проверки.
4. Подключить V2 к отдельному debug route или флагу, который рендер читает через snapshot-адаптер.
5. Сравнить V2 и legacy на сценариях, где legacy находится в своей области применимости; расхождение документировать, а не подгонять.
6. После принятия V2 мигрировать один базовый ручной сценарий, затем puzzle; старый kernel удалить только когда он не имеет потребителей.

## Последствия

- Новые базы, inverse design, физические формы и контентные расширения не блокируются навсегда, но не добавляются до прохождения первых fixtures.
- Часть существующих пазлов придётся перепроектировать: число витков больше не является ручкой сложности.
- Урамаки и тэмаки получают честный статус отдельных будущих моделей, а не частично работающих preset-ов.
- Документы, описывающие старую спиральную или кольцевую схему, остаются архивом и должны ссылаться на этот ADR как на точку смены контракта.

## Критерий принятия

Этот ADR станет `accepted` только после того, как ты подтвердишь область V2 и список сознательных не-целей. Реализация Core V2 не считается начатой до появления fixtures из этого документа.
