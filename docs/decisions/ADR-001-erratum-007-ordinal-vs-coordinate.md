## F07 — координата против порядкового номера

### Резолюция перекрытия (нужна для этого fixture, иначе acceptance ссылается на неопределённое поведение)

- `embedded` + `embedded`, **разный** `materialId`, пересекающийся footprint → **valid**. V2 alpha не моделирует объёмное исключение между разными веществами; итоговый композитинг слоёв — предмет отдельного ADR про `placement: 'stacked'` (issue #74), вне V2 alpha. Именно этот случай использует F07: оба патча тонкие, чтобы окно пересечения было маленьким и не превращало fixture в тест коллизий.
- `embedded` + `embedded`, **одинаковый** `materialId`, пересекающийся footprint → **`invalid: patch_material_overlap`**. Два патча одного вещества, занимающие одну и ту же точку листа, — это не композиция, а конфликтующее/задвоенное определение рецепта; корректная запись такой раскладки — один патч большего размера.
- `surface` над `embedded`, пересекающийся footprint по `(uMm, vMm)` → **valid**. Топпинг физически лежит поверх начинки; это ожидаемая композиция, а не конфликт.

Эта резолюция не трогает зарезервированную развилку про растяжение куска вместе с изгибающимся листом (STATE.md) — она о том, разрешено ли ДВУМ ТЕЛАМ занимать одну проекцию на листе, а не о том, как ведёт себя ОДНО тело при изгибе. Ничего в F07 не требует ответа на эту развилку.

### Вход

- База: `futomaki` (как в F05 — нужен запас по `placementWindowMm` (`nearEdgeMm`/`farEdgeMm`) по обе стороны от 60 мм).
- Патч-сосед `cucumber`, **неподвижный**: `uMm = 60`, `vMm = sheet.widthMm / 2`, `placement: 'embedded'`. `widthMm`/`heightMm` — из каталога, фиксируются численно после первого принятого запуска (как в F02).
- Патч-зонд `tamago`, **разный `materialId`**, `placement: 'embedded'`, тот же `vMm = sheet.widthMm / 2`. Заведомо тонкий: `widthMm` того же порядка или меньше, чем у соседа (фиксируется после первого запуска вместе с соседом), чтобы даже полное совпадение центров давало маленькое окно перекрытия, а не тест на объёмную коллизию.
- Серия из **девяти** рецептов, отличающихся только `uMm` зонда: `56, 57, 58, …, 64` мм — шаг 1 мм, ровно проходит через `uMm` соседа (60).
- Для каждого шага прогоняется пара рецептов с патчами в порядке `[cucumber, зонд]` и `[зонд, cucumber]`.
- Дополнительно один парный рецепт с **обменёнными** `uMm`: `uMm(cucumber) = 56`, `uMm(зонд) = 60`. Значение 56 — это первый шаг уже прогнанной девятки (не новое число), поэтому результат обменянного рецепта можно сверить напрямую с уже посчитанным шагом `uMm(зонд) = 56` без дополнительных прогонов. Не путать с перестановкой массива (F05) — здесь переставлены сами числа между двумя разными патчами, а не порядок элементов `patches`.
- Рука: `neutralHand`.

### Зачем нужен

Замер 03.09 (STATE.md:129-134): кусок проезжает 0,16 листа (≈34 мм) и на срезе не двигается ни на пиксель, потом прыгает на 0,624 R (≈15 мм) при смене порядка с соседом. Причина в коде — `geometry.js:2042` сортирует куски по `p.u`, `geometry.js:2069-2075` кладёт координату как сумму ширин предшественников: работает НОМЕР в порядке следования после сортировки, а не сама `uMm`. Ни F03, ни F05 этого не ловят: F03 двигает `uMm` единственного патча (полка из одного куска — не полка, `geometry.js:1944`), а F05 переставляет местами два независимых непересекающихся патча, для которых результат по построению не зависит от порядка что в дефектной реализации, что в исправленной. F07 — первый и единственный fixture, который заставляет `uMm` одного патча физически ПЕРЕСЕЧЬ `uMm` другого, поэтому только он может поймать зависимость от индекса после сортировки, а не от значения координаты.

### Приёмка

| Инвариант | Ожидание |
|---|---|
| Статус | `valid` на всех девяти шагах, для обоих порядков массива |
| Центр — функция только `uMm` | Для каждого шага центр и площадь зонда идентичны (в пределах `EPS_LENGTH_MM`) независимо от того, идёт зонд в `patches` до или после соседа |
| Непрерывность через пересечение | Для любых двух соседних шагов `|Δcenter_probe| ≤ |ΔuMm| + EPS_LENGTH_MM` (хорда не длиннее дуги при сохранении длины — инвариант 1; шаг 1 мм не даёт скачка ни до, ни после `uMm = 60`, включая сам момент совпадения координат) |
| Независимость соседа | Центр и площадь `cucumber` идентичны на всех девяти шагах — сосед не «отзывается» на приближение и прохождение зонда через его координату |
| Симметрия обмена — центр | Обменянный рецепт (`uMm(cucumber)=56`, `uMm(зонд)=60`) даёт: центр зонда равен центру, который `cucumber` имел на шаге `uMm=56` исходной серии; центр `cucumber` равен центру, который зонд имел на том же шаге. Точность — `EPS_LENGTH_MM`, а не более грубый `MAX_CENTER_DELTA_MM`: это один и тот же детерминированный расчёт `center = f(uMm)`, применённый к переставленным числовым входам одного и того же шага, а не сравнение двух разных шагов серии (там, где калибровался `MAX_CENTER_DELTA_MM` в F03) — совпадение обязано быть точным с точностью до floating-point, а не приближённым |
| Симметрия обмена — площадь (не меняется) | Площадь каждого патча в обменянном рецепте равна его собственной площади в исходном шаге `uMm=56` (`EPS_LENGTH_MM`): `area(cucumber)` не становится `area(зонда)` и наоборот. Площадь — функция `materialId`/каталожных размеров патча (тот же инвариант, что в F02, и явно заявлен самим F07 как «площадь = f(uMm) СВОЕГО патча»), а не его положения; обмен координатами двух патчей РАЗНОГО `materialId` не переносит их площади друг на друга. (Это отдельный пункт от предыдущего специально: смешивать «центр меняется местами» и «площадь меняется местами» в один тест некорректно — площадь двух разноматериальных патчей в общем случае разная, и требование «площади меняются местами» красило бы верную реализацию.) |
| Перекрытие в точке пересечения (`uMm = 60`) | Статус остаётся `valid` (разные `materialId`, см. «Резолюция перекрытия» выше); `visiblePatches` по-прежнему содержит два элемента с положительной площадью каждый |
| Честность same-material случая | Отдельно (не в развёртке по шагам): второй патч того же `materialId`, что и `cucumber`, с тем же `uMm = 60` → статус `invalid: patch_material_overlap`, диагностика называет оба id патчей |
| Детерминизм | `winding`/`section` hashes идентичны при повторном прогоне каждого шага |
| Чистота | Ни один из входных рецептов не мутирован после прогона |
