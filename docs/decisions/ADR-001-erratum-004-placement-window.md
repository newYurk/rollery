# ADR-001, Erratum 004 — «closure window» распадается на три величины: seamOverlapMm, tuckReachMm, placementWindowMm

- **Статус:** proposed; обязательное уточнение ADR-001 до реализации F02–F04.
- **Дата:** 2026-09-04.
- **Заменяет в ADR-001:** строку 34 («окно допустимого размещения начинки»), инвариант 5
  (строка 83), строки 92–93 таблицы «Поведение вне модели».
- **Заменяет в core-v2-fixtures.md:** `FixtureReport` (добавляет поле), F02 (вход), F03
  (вход и приёмка), F04 (вход и приёмка, фикстура разделена на F04a/F04b), таблицу mutation
  tests (одна новая строка).
- **Кому:** ревьюеру / разработчику Core V2. Термин `closure window` из контракта убран
  целиком — если он встретится в диффе после этого файла, это регресс, а не стиль.

## Проблема

Слово `closure window` в шести документах передачи называет минимум **два физически разных
предмета** и путается с третьим термином, который в контракте уже есть под своим именем:

1. **Шов обёртки** («Явный шов», инвариант 4; в `FixtureReport.seam`) — где нори физически
   стыкуется после намотки. Это уже определено координатами `uStartMm`/`uEndMm`/`angleRad`,
   но ADR-001:34 ставит слово «шов» рядом со словом «окно» в одной фразе, и это первое
   смешение.
2. **Предел досягаемости подворота** — измеренная 02.09 граница поведения модели: «одиночная
   начинка в ядре до u = 0,70, дальше едет в намотке» (STATE.md, раздел «02.09: ГИПОТЕЗА
   ОТКЛОНЕНА»). F03 в текущей редакции описывает именно этот эффект («ингредиент не двигался,
   затем скачком уходил к корке») как причину, зачем нужен fixture — но его приёмка говорит
   про «границу closure window», как будто это то же самое понятие, что и раскладка на листе.
3. **Окно допустимого размещения начинки на листе** — то, что нужно F02 («центрированный в
   closure window») и F04 («патч ... заведомо размещённый за пределами closure window») —
   единственное из трёх, которое сейчас нигде не имеет числа. Именно его отсутствие блокирует
   F02, единственный fixture PR1 с ингредиентом.

Это разные вещи с разными источниками, и одно слово на троих не проходит: F02/F04 требуют
числа для (3), а текст F03 написан про (2). Ни разу за все шесть документов эти числа не
разведены.

## Три величины вместо одной

### `seamOverlapMm` — не новая величина, а явное имя уже существующей

```ts
seam?: {
  uStartMm: number
  uEndMm: number
  angleRad: number
  overlapMm: number   // новое поле: uEndMm − uStartMm, неотрицательно
}
```

`seamOverlapMm` — это `seam.overlapMm`: длина шва вдоль листа, выводится из уже определённых
`uStartMm`/`uEndMm` инвариантом 4. Числа не требует и не источник поведения — источник
уже существующий подрядчик geometry. Единственное, что меняется этим erratum: слово «шов»
и слово «окно» в ADR-001:34 разводятся на разные предложения, чтобы шов больше не читался
как синоним closure window.

### `tuckReachMm` — предел досягаемости подворота, вычисляемый, не входной

```ts
// Measurements (kernel output), не Patch и не входной параметр рецепта
tuckReachMm: number   // граница «положение патча в ядре не меняет срез»
```

Источник: STATE.md, «02.09: ГИПОТЕЗА ОТКЛОНЕНА» — «одиночная начинка в ядре до u = 0,70,
дальше едет в намотке»; там же issue #139 переклассифицирован как продуктовый, не как дефект
модели («положение внутри досягаемости подворота на срез не влияет, потому что в жизни не
влияет»). Значение 0,70 — измеренный результат существующего уравнения подворота
(`geometry.js`, ветка `computeCore`/`sFold`, управляется `tuckMin` и длиной листа конкретной
базы), а не универсальная константа: для хосомаки (`sheetCm: 10.5`, `tuckMin: 3`) это
≈ 0,70 × `L`; для футомаки (другой `tuckMin`, другой `L`) число будет своим и должно
считаться той же формулой, а не копироваться как 0,70.

**`tuckReachMm` не является входом ни одного из F02–F04.** Это диагностика поведения модели
после намотки, а не критерий допустимости раскладки до неё. Ниже показано, что при
предложенном `placementWindowMm` для хосомаки (105 мм) легальная зона размещения
(до 52,5 мм от начала) целиком лежит внутри зоны нечувствительности подворота
(до ≈ 73,5 мм) — то есть ни один легальный по A5 патч не пересекает границу `tuckReachMm`,
и прыжок «к корке», которым сейчас объясняется F03, при легальной раскладке вообще не
воспроизводится. Это не довод против `tuckReachMm` как величины — это довод за то, чтобы
F03 тестировала непрерывность у **своей** границы (`placementWindowMm`), а не путала её с
чужой. Если позже понадобится fixture на сам прыжок подворота — это отдельный fixture с
`tuckReachMm` как входом, не переиспользование F03.

### `placementWindowMm` — окно раскладки на листе, ТРЕБУЕТ ПОДТВЕРЖДЕНИЯ ВЛАДЕЛЬЦА

```ts
// Constant per RecipeV2.sheet, вычисляется kernel'ом, попадает в FixtureReport
// Поля названы nearEdgeMm/farEdgeMm, а не uMinMm/uMaxMm — в FixtureReport уже есть
// sheet.uMinMm/uMaxMm (fixtures.md:32-33) с ДРУГИМ смыслом (границы фактической намотки).
// Erratum, весь смысл которого — прекратить путать разные величины одним именем,
// не должен создавать новую путаницу тем же способом на другом уровне вложенности.
placementWindowMm(sheet: { lengthMm: number }): { nearEdgeMm: number; farEdgeMm: number }
```

**Источник:** issue #57 / `docs/reality-check.md`, пункт A5 (четыре источника, включая
marron: 「具材を手前2cm位の場所から」「真ん中より上は敷かない」) — начинка кладётся не ближе
20 мм от ближней кромки листа (кромка, с которой начинается скрутка, `uMm = 0`) и не заходит
за середину листа.

**Кандидатное определение:**

```ts
const PLACEMENT_EDGE_MARGIN_MM = 20   // источник: A5 / marron, см. выше

function placementWindowMm(sheet) {
  return {
    nearEdgeMm: PLACEMENT_EDGE_MARGIN_MM,
    farEdgeMm: sheet.lengthMm / 2,
  }
}
```

Для F01–F04 (`sheet.lengthMm = 105`): `placementWindowMm = { nearEdgeMm: 20, farEdgeMm: 52.5 }`.

**Патч соответствует окну**, если весь его след на листе, а не только центр, лежит внутри:
`uMm − widthMm / 2 ≥ nearEdgeMm` и `uMm + widthMm / 2 ≤ farEdgeMm`. Частичное пересечение границы —
уже нарушение (снимает третье смешение из ADR-001:83 — «раскладка» там означает группу, а
F02–F04 проверяют один патч; групповая проверка теперь буквально: каждый патч группы по этому
же правилу, без отдельного «группового» понятия).

**⚠ Требует подтверждения владельца.** Число `PLACEMENT_EDGE_MARGIN_MM = 20` и правило
«верхняя граница = middle of sheet» — это кулинарный источник (A5), не физический вывод из
геометрии листа: их подтверждает четыре независимых рецептурных источника, но не измерение и
не инвариант сохранения. Открытый побочный вопрос — масштабируется ли `20 мм` с длиной листа
(как норисиро в `catalog.js:60`, `10/105 = 20/210`) для баз крупнее хосомаки; F01–F04 сейчас
все на хосомаки (105 мм), так что для первого PR это не блокер, но futomaki-fixture с окном
уже потребует ответа. **Один вопрос владельцу:** подтверждаешь `[20 мм от кромки, L/2]` как
окно раскладки для F02–F04, или у тебя другое ограничение (в частности — масштабируется ли
20 мм с длиной листа для более крупных баз)? До ответа разработчик реализует по этому
кандидату и явно фиксирует его как «предварительный, из A5» в PR-note (тот же паттерн, что
`EPS_LENGTH_MM` — developer-brief.md:108).

## Правки текста ADR-001

**ADR-001:34, было:**
> Явно определённый шов и окно допустимого размещения начинки.

**Стало:**
> Явно определённый шов (`seam`, инвариант 4) и отдельно — окно допустимого размещения
> начинки на листе (`placementWindowMm`, инвариант 5). Это разные величины: шов — про то, где
> замыкается обёртка после намотки; окно раскладки — про то, где на плоском листе игрок может
> положить начинку до намотки.

**ADR-001:83, инвариант 5, было:**
> **Ограниченная область применимости.** Если раскладка не помещается в closure window, kernel
> возвращает `invalid` или `outsideModelScope`; он не рисует идеальный ролл без диагностики.

**Стало:**
> **Ограниченная область применимости.** Если след патча выходит за физический край листа,
> kernel возвращает `invalid: patch_out_of_sheet`. Если след патча лежит на листе, но вне
> `placementWindowMm`, kernel возвращает `outsideModelScope: closure_window`. Эти два случая не
> взаимозаменяемы и проверяются раздельно (см. F04a/F04b). Kernel не рисует идеальный ролл без
> диагностики ни в одном из двух случаев.

**ADR-001:92–93, было:**

| Случай | Обязательный результат |
|---|---|
| Координата патча за пределами листа | `invalid: patch_out_of_sheet` |
| Группа вне closure window | `outsideModelScope: closure_window` |

**Стало:**

| Случай | Обязательный результат |
|---|---|
| След патча (не только центр `uMm`) выходит за `[0, sheet.lengthMm]` | `invalid: patch_out_of_sheet` |
| След патча целиком на листе, но не целиком внутри `placementWindowMm` | `outsideModelScope: closure_window` |

### F03 — было (строка 109–125)
Вход и приёмка через «границу closure window» без числа и без указания, о какой границе речь.

### F03 — стало

**Вход.** Серия из пяти рецептов, различающихся только `uMm` одного и того же патча огурца
(`widthMm = 14`, `catalog.js:305` × `U_MM = 5`, `catalog.js:205`). Проверка идёт по СЛЕДУ
патча (правило из предыдущего раздела: `uMm + widthMm/2 ≤ farEdgeMm`), не по его центру —
значит для этого патча реальная граница легальности не `farEdgeMm = 52.5`, а
`farEdgeMm − widthMm/2 = 52.5 − 7 = 45.5`. Пять значений `uMm` с шагом `ΔuMm = 1`, пересекающих
именно эту границу: `43.5, 44.5, 45.5, 46.5, 47.5`.

| `uMm` | след `[uMm−7, uMm+7]` | статус по правилу следа |
|---|---|---|
| 43.5 | [36.5, 50.5] | valid (50.5 ≤ 52.5) |
| 44.5 | [37.5, 51.5] | valid (51.5 ≤ 52.5) |
| 45.5 | [38.5, 52.5] | valid (52.5 ≤ 52.5, граница включительно) |
| 46.5 | [39.5, 53.5] | outsideModelScope (53.5 > 52.5) |
| 47.5 | [40.5, 54.5] | outsideModelScope (54.5 > 52.5) |

Если приёмку писать через центр (`uMm ≤ 52.5`), все пять значений формально «пересекают
52.5» на бумаге, но по правилу следа, которое контракт уже принял для F04b, они все вне окна
одинаково — серия останется таким же немым тестом, каким закрываемая находка называла F03
до этого erratum, просто по числовой причине вместо терминологической. Приёмка ниже считает
границу по следу, не по центру, чтобы этого не случилось.

**Зачем нужен.** Проверяет, что переход из легальной зоны раскладки в нелегальную не
маскируется — kernel обязан либо остаться непрерывным по центру/площади патча внутри
легальной зоны, либо явно назвать границу до разрыва. Это **не** проверка прыжка подворота
(`tuckReachMm` ≈ 0,70 × `L` ≈ 73,5 мм для того же листа): вся серия F03 (след до 54,5 мм)
лежит внутри зоны нечувствительности подворота, и это преднамеренно — иначе fixture проверял
бы сразу две разные границы одним прогоном и не мог бы отличить их причины.

**Приёмка:**

- Для двух соседних валидных входов (`uMm = 43.5` и `44.5`, оба со следом внутри
  `[nearEdgeMm, farEdgeMm]`) изменение центра и площади ограничено явно заданными порогами
  `MAX_CENTER_DELTA_MM` и `MAX_AREA_RATIO_DELTA` (пороги без изменений — не предмет этого
  erratum).
- При `uMm = 45.5` (след `[38.5, 52.5]`, граница включительно) статус — `valid`.
- При `uMm = 46.5` (след `[39.5, 53.5]`, впервые превышает `farEdgeMm`) статус меняется на
  `outsideModelScope: closure_window`.
- Переход `valid → outsideModelScope` (между `uMm = 45.5` и `46.5`) не сопровождается валидным
  срезом с беспричинным скачком положения или площади предыдущего валидного входа.
- В отчёте каждого прогона указан `report.placementWindowMm` (одинаковый для всей серии, раз
  лист один и тот же) и, при отказе, причина.

## Причина

Без числа для `placementWindowMm` F02 не собирается — это единственный вход всего пакета
F01–F06, который требует ингредиент не «где угодно на листе», а именно «в допустимом окне»,
и до этого erratum такого числа не было нигде в репозитории, кроме самого слова в тексте.
Без разделения на `seamOverlapMm`/`tuckReachMm`/`placementWindowMm` разработчик, реализующий
F03, с равной вероятностью подключит либо границу шва, либо границу подворота, либо
несуществующее число — и все три дадут разный зелёный/красный на одних и тех же fixtures.
