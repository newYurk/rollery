# ADR-001, Erratum 008 — направление намотки объявляется явно, не подразумевается

- **Статус:** proposed; обязательное уточнение ADR-001 до завершения текущего ревью ветки `architecture/core-v2-foundation`.
- **Нумерация:** это Erratum **008**. Ночь 03–04.09 заняла номера 004–007 параллельными
  правками контракта (004 — `placementWindowMm`, 005 — `seamOverlapMm`/`overlapArcRad`, 006 —
  якорь площади к каталогу, 007 — fixture F07 «координата против порядкового номера»). Эта
  правка ортогональна всем им: та часть, что про ГДЕ на листе можно класть начинку (004), КАКОЙ
  нахлёст у шва (005), КАКАЯ площадь у куска (006), КАКОЙ порядок укладки (007) — не про то же,
  что здесь: В КАКОМ НАПРАВЛЕНИИ лист читается вдоль уже согласованной оси `u`. Термины ниже
  используют новые имена из Erratum 004 (`placementWindowMm.nearEdgeMm`/`farEdgeMm`) везде, где
  вообще упоминается окно раскладки; старые `closure window`/`uMinMm`/`uMaxMm` в значении «окно
  раскладки» в этом документе не используются. Новый fixture этой правки называется **F08**, не
  F07 — F07 уже занят erratum-007 (проверка порядка укладки, другое содержание).
- **Заменяет в ADR-001:** раздел «Контракт рецепта» (добавляет поле `windDirection` в `RecipeV2`), раздел «Инварианты» (добавляет пункт 10 — пункт 9 уже занят `ADR-001-erratum-006-area-anchor.md`, заглушка резерва владельца; написано независимо той же ночью, коллизия найдена третьим сводным прогоном ревью), раздел «Поведение вне модели» (добавляет строку).
- **Дополняет `core-v2-fixtures.md`:** новый fixture F08; новая строка в таблице mutation tests; **обязательное добавление поля `windDirection` в «Вход» каждого из F01, F02, F03, F04a, F04b, F05** (см. раздел ниже — без этого правки самопротиворечивы: новое правило «поле обязательно» делает существующие «Вход»-блоки невалидными по их же собственной приёмке `valid`); правка «Вход»/приёмки F06; правка ссылок «F01–F06» → «F01–F08».
- **Закрывает:** `core-v2-validation-findings.md`, пропущенный класс «Направление намотки вдоль uMm» (blocker); issue #93 «Скрутка: снизу вверх зафиксировано, остаётся выбор конца оси» — тот же вопрос, см. «Один вопрос, не два» ниже.
- **Кому:** ревьюеру / разработчику Core V2.

## Разбор находки

`Patch.uMm` — координата вдоль оси скрутки, но контракт нигде не говорит, какой конец этой оси наматывается первым (уходит к сердцевине, `s = 0` в инварианте 3) и какой — последним (остаётся снаружи, рядом со швом). Разворот этой конвенции («u=0 первый» ↔ «u=0 последний») не меняет ни одно измерение, которое проверяют F01–F06:

- длина покрытия листа не меняется — переворот не создаёт и не убирает длину;
- число швов не меняется — шов один в обоих случаях;
- hash при повторных запусках ОДНОЙ и той же (пусть и не объявленной) конвенции не меняется — детерминизм внутри одного молчаливого выбора сохраняется.

Меняется только то, что ни один инвариант 1–8 не измеряет: какая физическая сторона листа оказывается у сердцевины ролла — то есть зеркальность рисунка на срезе. Два kernel-а, построенные на противоположных необъявленных конвенциях, оба проходят F01–F06 и выдают зеркальные срезы из одного и того же `RecipeV2`.

## Один вопрос, не два

Issue #93 формулирует это как «конец оси скрутки» и предлагает то же лечение: «либо полем `RecipeV2`, либо явной нормализацией `u` при компиляции рецепта (`u → L − u`)». У ролла один осмысленный «оборотный» параметр — в каком порядке накопленная длина дуги `s` растёт вдоль `uMm` (инвариант 3: `uMm → sMm → θ`). Направление возрастания `s` относительно `uMm` — это и есть «конец оси» (#93), и это же — «handedness/направление намотки» (эта находка): оба вопроса спрашивают «при `s=0` (первый виток, у сердцевины) какому концу диапазона `[0, L]` соответствует `uMm`?». Это не два независимых поля, а одна и та же степень свободы, названная в триаже и в адверсариальном ревью разными словами. Один вопрос — одно поле ниже закрывает и находку, и #93.

Заголовок #93 — «снизу вверх зафиксировано» — по тексту issue-triage.md относится к уже решённой оси; какой физический жест он называет буквально, по документам трекера не устанавливается однозначно, и это не критично для вывода выше: вывод «один вопрос, не два» опирается на прямое совпадение формулировок задачи («конец оси скрутки» = «при `s=0` какому концу `[0, L]` соответствует `uMm`»), а не на интерпретацию заголовка. Не путать это со **зафиксированной осью `vMm`**: `ADR-001-erratum-002-no-diagonal-placement.md:23` прямо определяет `vMm` как «центр вдоль оси ролла» (длина готового цилиндра, номер среза) — это не ось подворота/сгиба листа и не тот же вопрос, что здесь.

## Нужен ли отдельный вопрос владельцу

Нет. Это не зарезервированный вопрос из STATE.md («растягивается ли кусок начинки вместе с изгибающимся листом, или лист несёт длину дуги отдельно, а кусок хранит форму и площадь и проскальзывает») — тот вопрос про физику куска при изгибе листа (issue #134), этот — про то, какой конец уже согласованной оси `u` считается началом намотки. Выбор между `fromUZero` и `fromULength` не физический факт о материале, а конвенция координат: обе дают одинаково корректную геометрию, разница только в том, что одна — зеркало другой. Контракт обязан зафиксировать одну (неважно какую) и сделать её частью сериализуемого рецепта, чтобы не воспроизвести тот же баг (невидимая конвенция) под новым именем.

## Правка `RecipeV2`

**Было** (ADR-001-core-v2-scope.md, состояние после Erratum 002):

```ts
type RecipeV2 = {
  version: 2
  baseId: string
  sheet: { lengthMm: number; widthMm: number }
  wrap: { materialId: string }
  rice: { profileId: string }
  patches: Patch[]
  hand: NeutralHand | RecordedHand
}
```

**Стало:**

```ts
type RecipeV2 = {
  version: 2
  baseId: string
  sheet: { lengthMm: number; widthMm: number }
  wrap: { materialId: string }
  rice: { profileId: string }
  windDirection: WindDirection
  patches: Patch[]
  hand: NeutralHand | RecordedHand
}

// Какой конец диапазона uMm ∈ [0, L] наматывается первым (ближе к сердцевине,
// s = 0 в инварианте 3), а какой — последним (снаружи, ближе к шву).
// 'fromUZero'   — uMm = 0 наматывается первым, uMm = L — последним.
// 'fromULength' — uMm = L наматывается первым, uMm = 0 — последним.
type WindDirection = 'fromUZero' | 'fromULength'
```

Поле обязательно. Отсутствующее или не входящее в перечисление значение — `invalid: recipe_missing_wind_direction`, до любой попытки построить wind-state.

### Значение по умолчанию для V2 alpha

Для F01–F08 используется одно значение — `windDirection: 'fromUZero'` — во всех fixtures, кроме специально предназначенного для проверки переворота F08. Основание для выбора именно этого направления, а не произвольное: `play/model/geometry.js:1229–1252` (legacy `wind()`, цикл `for (let шаг = 0; шаг < KMAX * NB && sп < L; шаг++) { ... }`). Конкретно строка `const r = (k === 0) ? r0e + t0 * (шаг * DPHI) / TAU : top[b];` — для первого витка (`k === 0`) радиус `r` растёт вместе с `шаг` от `r0e` (сердцевина) наружу; и строка `u0[idx] = sп / L` — накопленная длина дуги `sп` монотонно растёт вместе с `шаг` в том же цикле. Значит меньший `sп` (и меньший `u0 = sп / L`) откладывается на меньший радиус — наматывается первым, ближе к сердцевине. `fromUZero` продолжает то же соответствие «малый `u` → внутренний виток», а не изобретает новое — это упрощает сравнение V2 и legacy на шаге 5 плана миграции ADR-001 («расхождение документировать, а не подгонять»). Значение — конвенция, а не физический факт: утверждения владельцем не требует (см. выше), но обязано быть записано здесь, а не только выбрано в коде.

## Правка «Инварианты» — новый пункт 10

**10. Явное направление намотки.** Соответствие между `uMm` и накопленной длиной дуги `sMm` из инварианта 3 однозначно ориентировано полем `RecipeV2.windDirection`. Смена значения этого поля при неизменных `patches` обязана менять `winding` hash и `section` hash (см. mutation test и F08 в `core-v2-fixtures.md`). Реализация, которая строит `s(u)` не читая `windDirection` — то есть жёстко зашивает одно направление в коде, — нарушает этот инвариант, даже если все её fixtures зелёные хотя бы для одной конвенции.

## Правка `core-v2-fixtures.md`

### Обязательное добавление `windDirection` в «Вход» существующих fixtures

Поле `windDirection` в `RecipeV2` теперь обязательно (см. выше), а «Вход» каждого fixture в `core-v2-fixtures.md` — это **нормативный исполняемый сценарий**, не иллюстрация из ADR-текста. Без этой правки F01–F05 (и, транзитивно, F06) требуют одновременно `status: valid` и, по буквальному новому правилу («отсутствующее значение → `invalid: recipe_missing_wind_direction`, до любой попытки построить wind-state»), `status: invalid` — то есть противоречат сами себе, и разработчик либо ломает пять ранее зелёных fixtures, либо молча достраивает недостающее поле собственным значением по умолчанию, воспроизводя ровно тот необъявленный выбор конвенции, ради искоренения которого пишется этот erratum. Ниже — точная правка каждого затронутого «Вход»-блока. Правки применяются поверх текста F02/F03/F04a/F04b, установленного `ADR-001-erratum-004-placement-window.md` (окно раскладки уже расщеплено там; здесь оно не меняется).

**F01 — пустой хосомаки.** В «Вход» добавляется строка:

- `windDirection: 'fromUZero'`

(Патчей нет, но поле — часть `RecipeV2`, а не `Patch`, и обязательно независимо от того, есть ли начинка.)

**F02 — один огурец в центре допустимого окна.** В «Вход» (после строки про `placementWindowMm`, `ADR-001-erratum-004-placement-window.md`) добавляется строка:

- `windDirection: 'fromUZero'`

**F03 — непрерывность у границы окна раскладки.** Все пять рецептов серии (`uMm = 43.5, 44.5, 45.5, 46.5, 47.5` из Erratum 004) используют одно и то же значение:

- `windDirection: 'fromUZero'` — константа по всей серии; меняется только `uMm`. (Если бы `windDirection` менялся вместе с `uMm`, F03 проверял бы сразу две независимые оси одним прогоном и не мог бы приписать наблюдаемый скачок ни одной из них — та же ошибка смешения, которую Erratum 004 уже исправил для `tuckReachMm`/`placementWindowMm`.)

**F04a — патч за физическим краем листа.** В «Вход» добавляется строка:

- `windDirection: 'fromUZero'`

**F04b — патч внутри листа, но вне окна раскладки.** В «Вход» добавляется строка:

- `windDirection: 'fromUZero'`

**F05 — футомаки с рядом независимых ингредиентов.** В «Вход» добавляется строка, **одинаковая для обоих рецептов пары** (базового `[A, B, C]` и переставленного `[C, A, B]`):

- `windDirection: 'fromUZero'` — одно и то же значение в обоих рецептах пары.

Одинаковость обязательна: F05 проверяет инвариантность к перестановке патчей в массиве; если бы у пары был разный `windDirection`, различие hash можно было бы (ошибочно) списать на порядок патчей, а не опознать как эффект другого поля — это увело бы приёмку F05 в сторону, которую и должен предотвращать явно записанный F08 ниже.

### Новый раздел — F08 — направление намотки не молчаливое

#### Вход

- База: `futomaki`
- Патчи: тот же набор патчей, что задаётся в F05 (когда он будет конкретизирован численными `uMm`/`id`/`materialId` при первом принятом запуске F05) — без изменений между R1 и R2
- Рецепт R1: `windDirection: 'fromUZero'`
- Рецепт R2: та же геометрия листа и те же `patches`, но `windDirection: 'fromULength'`
- Рука: `neutralHand`

#### Зачем нужен

F05 доказывает, что порядок патчей в массиве не является скрытым физическим контрактом. F08 доказывает обратное по смыслу: `windDirection` — единственное поле, которое обязано менять итог, потому что это и есть объявленная физическая ориентация листа. Реализация, которая читает `uMm` в `θ` одним и тем же способом независимо от `windDirection` (трактует поле как декоративное), проходит все остальные fixtures (F01–F07, включая проверку порядка укладки из F07 — та ось про порядковый номер патчей, эта про направление намотки, они независимы) и молчаливо выдаёт зеркальный узор — ровно тот баг, ради которого заведён этот fixture.

#### Приёмка

| Инвариант | Ожидание |
|---|---|
| Статус R1 и R2 | `valid` |
| Геометрия листа | Все проверки F01 зелёные для обоих рецептов независимо |
| Hash | `winding` и `section` hash R1 и R2 обязаны различаться |
| Центры | Для каждого id патча `centerXmm`/`centerYmm` в R2 не совпадают с R1 в пределах `EPS_LENGTH_MM`; конкретное геометрическое соотношение (зеркало вокруг плоскости шва) фиксируется числом после первого принятого запуска, по образцу F02 |
| Согласованность с F05 | Реализация обязана одновременно проходить F05 (перестановка патчей → тот же hash) и НЕ проходить условие равенства в F08 — если у реализации совпадают и hash F05, и hash F08, она игнорирует `windDirection` |
| Честный отказ на пропуск поля | Рецепт без `windDirection` (или с посторонним значением) → `invalid: recipe_missing_wind_direction`, а не молчаливый выбор конвенции по умолчанию |

## Что ревью не должно рекомендовать

- оставлять направление намотки неявным в коде «раз уж legacy делает именно так» — legacy не oracle (`core-v2-legacy-boundary.md`), F08 обязан проверяться на уровне контракта независимо от совпадения с legacy;
- закрывать issue #93 переводом в NEEDS OWNER DECISION — это контрактный пробел, лечится этим erratum, а не продуктовой развилкой;
- путать эту находку с F05 (порядок независимых патчей в массиве) — F05 про инвариантность к перестановке, F08 про чувствительность к объявленному развороту; обе проверки должны существовать одновременно, не подменяя друг друга;
- путать `windDirection` с зарезервированным вопросом STATE.md про растяжение куска при изгибе листа (issue #134) — это разные степени свободы модели;
- принимать новое обязательное поле только прозой в ADR-тексте («Значение по умолчанию для V2 alpha») без переноса в исполняемые «Вход»-блоки `core-v2-fixtures.md» — именно fixtures.md, а не ADR, нормативен для приёмки, и разошедшийся с ним ADR-текст воспроизводит тот же класс бага (невидимая, недокументированная в исполняемом сценарии конвенция), который весь этот erratum призван закрыть.
