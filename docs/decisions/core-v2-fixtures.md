# Core V2 fixtures — исполнимые сценарии приёмки

- **Статус:** proposed
- **Связанный документ:** `ADR-001-core-v2-scope.md`
- **Назначение:** это нормативные сценарии для нового forward-kernel. Они не описывают UI, визуальный стиль или реализм каждого ингредиента.

## Правила fixtures

Каждый fixture — неизменяемый входной `RecipeV2`, ожидаемые статусы и измеримые инварианты.

- Все координаты и размеры хранятся в миллиметрах.
- Каждый fixture прогоняется минимум два раза в одном окружении.
- `neutralHand` — единственный допустимый профиль руки.
- Проверка не должна сравнивать canvas-пиксели. Она сравнивает доменные измерения и детерминированный hash карты материалов.
- Любая реализация, которая проходит fixture лишь за счёт подгонки ожидаемого числа, но нарушает общий инвариант, считается неверной.
- `legacy` можно использовать только как визуальный reference в зоне его применимости; legacy-числа не являются истиной для V2.

## Общий отчёт

Каждый прогон обязан вернуть:

```ts
type FixtureReport = {
  fixtureId: string
  status: 'valid' | 'invalid' | 'outsideModelScope' | 'unsupported'
  diagnostics: Diagnostic[]
  sheet: {
    lengthMm: number
    coveredLengthMm: number
    uncoveredLengthMm: number
    phantomLengthMm: number
    uMinMm: number
    uMaxMm: number
  }
  seam?: { uStartMm: number; uEndMm: number; angleRad: number }
  roll?: { diameterMinMm: number; diameterMaxMm: number; wrapIntersectionsByRay: number[] }
  visiblePatches: Array<{ id: string; areaMm2: number; centerXmm: number; centerYmm: number }>
  hashes: { recipe: string; winding: string; section: string }
}
```

### Общие обязательные проверки

| Проверка | Правило |
|---|---|
| Конечность | Все числа отчёта конечны; нет `NaN`, `Infinity`, отрицательной длины или площади |
| Границы листа | Для валидной намотки `0 ≤ uMinMm ≤ uMaxMm ≤ sheet.lengthMm` |
| Сохранение длины | `uncoveredLengthMm` и `phantomLengthMm` не превышают численный допуск |
| Повторяемость | Повтор одного fixture даёт одинаковые `winding` и `section` hashes |
| Чистота | Входной `RecipeV2` не изменён после прогона |
| Порядок патчей | Если два независимых патча поменяны местами в массиве, результат не меняется |
| Честный отказ | Неподдерживаемый или внеобластной случай не возвращает `valid` |

Численный допуск для сохранения длины задаётся константой `EPS_LENGTH_MM`, обоснованной разрешением дискретизации. Он должен быть явно выведен в отчёте; нельзя использовать неименованное сравнение с нулём.

## F01 — пустой хосомаки

### Вход

- База: `hosomaki`
- Один лист нори длиной 105 мм
- Стандартная рисовая постель базы
- Патчи: `[]`
- Рука: `{ mode: 'neutral', seed: 0 }`
- Срез: центральный, `vSliceMm = sheet.widthMm / 2`

### Зачем нужен

Это минимальная проверка самой карты листа. Здесь нельзя спрятать ошибку длины под влиянием начинки, группы или порядка укладки.

### Приёмка

| Инвариант | Ожидание |
|---|---|
| Статус | `valid` |
| Покрытие листа | `coveredLengthMm = 105 ± EPS_LENGTH_MM` |
| Фантомная длина | `phantomLengthMm ≤ EPS_LENGTH_MM` |
| Потерянная длина | `uncoveredLengthMm ≤ EPS_LENGTH_MM` |
| Координаты | `uMinMm ≥ 0`, `uMaxMm ≤ 105` |
| Шов | Существует и находится на листе |
| Нори по лучу | Ровно одно пересечение на всех лучах, кроме явно выделенной угловой окрестности шва |
| Повтор | Результирующие hashes идентичны |

## F02 — один огурец в центре допустимого окна

### Вход

- База: `hosomaki`
- Один осевой патч огурца, центрированный в closure window
- Все размеры ингредиента берутся из текущего каталога, но в fixture после первого принятого запуска фиксируются численно
- Рука: `neutralHand`

### Зачем нужен

Проверяет, что kernel умеет перенести реальный объект с листа на срез без скачка, исчезновения или зависимости от FPS и глобального состояния.

### Приёмка

| Инвариант | Ожидание |
|---|---|
| Статус | `valid` |
| Геометрия листа | Все проверки F01 остаются зелёными |
| Видимость | В отчёте ровно один `visiblePatch` с id огурца |
| Площадь | `areaMm2 > 0` и стабильна между повторными запусками |
| Центр | Координаты центра конечны и стабильны между повторными запусками |
| Детерминизм | `winding` и `section` hashes совпадают между прогонами |
| Чистота | Рецепт и патч не мутированы |

## F03 — непрерывность у границы closure window

### Вход

Серия минимум из пяти рецептов, различающихся только `uMm` одного и того же огурца. Последовательность пересекает границу closure window с малым фиксированным шагом `ΔuMm`.

### Зачем нужен

Текущая модель демонстрировала запрещённое поведение: ингредиент не двигался, затем скачком уходил к корке и резко терял площадь. V2 должна либо быть непрерывной в поддерживаемой области, либо явно назвать границу модели до скачка.

### Приёмка

- Для двух соседних валидных входов изменение центра и площади ограничено явно заданными порогами `MAX_CENTER_DELTA_MM` и `MAX_AREA_RATIO_DELTA`.
- Пороги измеряются и выбираются до реализации визуальной полировки; они не подгоняются после первого провала.
- Если очередной вход выходит из области, статус меняется на `outsideModelScope: closure_window`.
- Переход `valid → outsideModelScope` не сопровождается валидным срезом с беспричинным скачком положения или площади.
- В отчёте указан `closureWindow` и причина отказа.

## F04 — патч вне области модели

### Вход

- База: `hosomaki`
- Тот же патч огурца, заведомо размещённый за пределами closure window либо частично за физическим краем листа
- Рука: `neutralHand`

### Зачем нужен

Проверяет не красоту невозможного результата, а честность модели. Система не имеет права скрытно исправлять или интерпретировать такой рецепт как другой.

### Приёмка

| Инвариант | Ожидание |
|---|---|
| Статус | `invalid: patch_out_of_sheet` или `outsideModelScope: closure_window` |
| Диагностика | Содержит id патча, нарушенную границу и наблюдаемое значение |
| Срез | Не возвращается как `valid` |
| Fallback | Нет автоматического перемещения, обрезания или замены базы |
| Повтор | Одинаковый тип отказа и одинаковый diagnostic code |

## F05 — футомаки с рядом независимых ингредиентов

### Вход

- База: `futomaki`
- Ряд из нескольких не перекрывающихся патчей с фиксированными id и материалами
- Порядок патчей в одном рецепте: `[A, B, C]`
- Парный рецепт: `[C, A, B]`, все остальные данные идентичны
- Рука: `neutralHand`

### Зачем нужен

Порядок объектов в массиве не должен быть скрытым физическим контрактом, если речь не идёт о явно заданной укладке по слоям. Это ловит ошибку «последний в массиве выиграл» и делает правила укладки явными.

### Приёмка

| Инвариант | Ожидание |
|---|---|
| Статус обоих рецептов | `valid` |
| Геометрия листа | Все проверки F01 зелёные |
| Порядок | Одинаковые `winding` и `section` hashes |
| Видимые патчи | Совпадают id, площади и центры в пределах допуска |
| Если порядок должен влиять | В fixture обязательно задано явное поле `layer`/`placementOrder`; один порядок массива сам по себе не является таким полем |

## F06 — полная воспроизводимость

### Вход

Каждый fixture F01–F05 выполняется дважды в одной сессии и один раз после создания нового экземпляра kernel. Входы сериализуются и десериализуются между запусками.

### Зачем нужен

Пазл и ссылки на рецепты требуют, чтобы одинаковый рецепт означал одинаковый срез. Случайность, текущее время, частота кадров, порядок кеша и остаточное глобальное состояние не могут менять итог.

### Приёмка

- `RecipeV2` после round-trip сериализации даёт тот же `recipe` hash.
- Все три запуска имеют идентичные `winding` и `section` hashes.
- Все measurements совпадают строго либо в пределах заранее заданного численного допуска.
- Отключение/очистка кеша не меняет результат.
- Преднамеренная замена `seed`, если и когда V2 начнёт поддерживать `RecordedHand`, обязана менять результат объяснимо и только в соответствующем режиме. До отдельного ADR V2 принимает только `neutralHand`.

## Mutation tests

Fixtures считаются доказательными только если намеренная поломка делает их красными. До подключения V2 к UI нужно выполнить и сохранить результаты следующих мутаций:

| Мутация | Что обязано упасть |
|---|---|
| Добавить к отображению `uMm` постоянный сдвиг за конец листа | F01: границы и фантомная длина |
| Заменить параметризацию по дуге на пропорцию номера бина | F01/F02: сохранение длины |
| Добавить `Math.random()` при построении wind-state | F06: hashes |
| Мутировать входной патч внутри kernel | F02/F06: чистота |
| Сделать последний патч массива победителем без явного layer | F05: инвариант порядка |
| Заменить outside-scope отказ на центрирование патча | F04: честный отказ |
| Принудительно задать puzzle `turns` как источник длины | F01/F06 и отдельный puzzle adapter test |

## Что не проверяется здесь

- Внешняя правдоподобность материалов в фотографии.
- Реальная механика рук, давление, разрушение и проскальзывание.
- Финальная форма и художественная отрисовка среза.
- Урамаки, тэмаки, кадзари-маки и вложенные роллы.
- Качество пазловых уровней и метрика их интересности.

Эти вопросы важны, но смешивание их с проверкой карты листа снова сделает фундамент непроверяемым.

## Критерий готовности V2 alpha

Core V2 можно подключать к отдельному debug-рендеру только когда F01–F06 и все mutation tests проходят автоматически. Подключение к основному ручному режиму, пазлу, inverse design или миграция старых рецептов требуют отдельного решения после этого порога.
