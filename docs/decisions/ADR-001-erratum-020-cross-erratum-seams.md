# ADR-001 — Erratum 020: три стыка между erratum 008/013/014/015

- **Дата:** 2026-09-04
- **Статус:** proposed; точечная правка трёх мест, где отдельно верные erratum (013, 014,
  015) при чтении вместе с 004/008/019 расходятся. Не блокер: осторожный разработчик, читающий
  прозу, а не только «Было»/«Стало» построчно, соберёт F01/F02 верно и без этого erratum —
  но механическая сборка контракта («Стало» как буквальный текст) — нет.
- **Уточняет (поверх `ADR-001-erratum-015-f02-catalog-area-formula.md`, Патч 1):** «Было»/
  «Стало» входа F02.
- **Уточняет (поверх `ADR-001-erratum-008-wind-direction.md`):** тип `WindDirection`
  (комментарий) и абзац «Значение по умолчанию для V2 alpha».
- **Уточняет (поверх `ADR-001-erratum-013-sheet-parameter-vs-layer-arc.md`, Патч 1 и
  Патч 2):** формулировку интеграла по средней линии слоя в инварианте 1 и в приёмке F01.
- **Уточняет (поверх `ADR-001-erratum-014-core-box-units.md`, «Проблема», Патч 1, «Новая
  константа» и «Предупреждение»):** число асимметрии ядра (было по осям, 1,1 мм; верно по
  всем лучам, в углу коробки, 1,88 мм) — во всех местах документа, где оно встречается.
- **Источник:** независимый ревьюер-человек, issue [#171](https://github.com/newYurk/rollery/issues/171),
  третий прогон (`PASS WITH GAPS` на накопленном 001–019). Проверено независимо каждое из
  четырёх мест — см. ниже.
- **Связанные документы:** `ADR-001-erratum-004-placement-window.md`,
  `ADR-001-erratum-006-area-anchor.md`, `ADR-001-erratum-008-wind-direction.md`,
  `ADR-001-erratum-013-sheet-parameter-vs-layer-arc.md`,
  `ADR-001-erratum-014-core-box-units.md`, `ADR-001-erratum-015-f02-catalog-area-formula.md`,
  `ADR-001-erratum-019-invertibility-seam-cut.md`, `play/model/catalog.js`,
  `play/model/geometry.js`.

## Общая причина

Все три (плюс один минорный) — не новые баги в физике или в отдельном файле: каждый erratum
013–015 верен внутри себя и был адверсарно проверен внутри себя. Дыра — на стыке: черновик
013/014/015 цитировал код или предыдущий erratum, не перечитав его точно, тем же классом
ошибки, что Слой 5 ловил у erratum-010 (см. `docs/handoff/core-v2-validation-findings.md`,
Слой 5, находки 1–3). Поштучная адверсарная проверка каждого erratum по своему контрпримеру
это структурно не видит — нужен свод.

## Патч 1 — «Было»/«Стало» входа F02 (поверх `erratum-015`, Патч 1)

**Проблема.** `erratum-015` взял «Было» из непатченного `core-v2-fixtures.md` (бытовое
«центрированный в closure window»), а не из накопленного состояния после `erratum-004`
(переименовал в `placementWindowMm`, добавил `uMm = 36.25`) и `erratum-008` (добавил
`windDirection` во «Вход» F02, `erratum-008-wind-direction.md:108-110`, сразу после строки
про `placementWindowMm`). Механическая замена «Было» → «Стало» из `erratum-015` как есть
откатывает термин, за который первый прогон ревью выносил `FAIL`, и роняет `uMm = 36.25`.

Было (текущий, ошибочный, блок `erratum-015`, Патч 1):

```markdown
- База: `hosomaki`
- Один осевой патч огурца, центрированный в closure window
- Все размеры ингредиента берутся из текущего каталога, но в fixture после первого принятого запуска фиксируются численно
- Каталожная площадь поперечного сечения патча в состоянии покоя фиксируется как `catalogAreaMm2`. В отличие от `widthMm`/`lengthMm`, которые читаются из каталога напрямую, `catalogAreaMm2` **вычисляется по формуле каталожной геометрии** (площадь сечения по каталожным `widthMm`/`heightMm`/форме, независимо от kernel-конвейера намотки и среза) — а не берётся как `visiblePatch.areaMm2` из первого прогона самого kernel. Фразой «фиксируются численно после первого принятого запуска» описывается только то, что итоговое число один раз замораживается в тексте fixture ради стабильности файла — не то, откуда это число берётся. Если источником станет первый прогон kernel, а не независимая формула, «якорь» замораживает результат самого kernel (включая любую его систематическую ошибку на момент этого прогона) как эталон — и вся проверка вырождается в тот же паттерн «сосед сравнивается с соседом», который эта правка и должна закрыть, просто на один уровень глубже.
- Рука: `neutralHand`
```

Стало (правильно накопленное состояние: `erratum-004` переименовал строку 2 и дал `uMm`,
`erratum-008` вставил `windDirection` сразу после неё, `erratum-006` вставил абзац
`catalogAreaMm2` после строки про фиксацию размеров, `erratum-015` добавляет свою формулу
последней перед «Рука» — порядок вставок именно такой, каждый erratum анкерился на текст
предыдущего, а не на позицию):

```markdown
- База: `hosomaki`
- Один осевой патч огурца, центрированный в `placementWindowMm`: `uMm = (placementWindowMm.nearEdgeMm + placementWindowMm.farEdgeMm) / 2` — для `sheet.lengthMm = 105` это `uMm = 36.25` (Erratum 004)
- `windDirection: 'fromUZero'` (Erratum 008)
- Все размеры ингредиента берутся из текущего каталога, но в fixture после первого принятого запуска фиксируются численно
- Каталожная площадь поперечного сечения патча в состоянии покоя фиксируется как `catalogAreaMm2`. В отличие от `widthMm`/`lengthMm`, которые читаются из каталога напрямую, `catalogAreaMm2` **вычисляется по формуле каталожной геометрии** (площадь сечения по каталожным `widthMm`/`heightMm`/форме, независимо от kernel-конвейера намотки и среза) — а не берётся как `visiblePatch.areaMm2` из первого прогона самого kernel. Фразой «фиксируются численно после первого принятого запуска» описывается только то, что итоговое число один раз замораживается в тексте fixture ради стабильности файла — не то, откуда это число берётся. Если источником станет первый прогон kernel, а не независимая формула, «якорь» замораживает результат самого kernel (включая любую его систематическую ошибку на момент этого прогона) как эталон — и вся проверка вырождается в тот же паттерн «сосед сравнивается с соседом», который эта правка и должна закрыть, просто на один уровень глубже (Erratum 006)
- Формула для F02 (Erratum 015): `catalogAreaMm2 = wU × hU × cutFill(d) × U_MM²`, где `cutFill(d)` — та же функция доли вещества от каталожного объекта начинки `d` (не от строки `cut`), что уже определена в `play/model/geometry.js`. Огурец: `cut: 'сектор'` (`catalog.js:305`), `cutFill(d) ≈ 0,555` (значение — из `geometry.js:557-559`, не из `catalog.js`). НЕ `wU × hU × U_MM²` без `cutFill` — это площадь описанного прямоугольника, не сектора. Для F02: `wU = 2.8`, `hU = 1.98`, `U_MM = 5` → `catalogAreaMm2 = 2,8 × 1,98 × 0,555 × 25 ≈ 76,9 мм²`. Разработчик вычисляет число вызовом той же формулы/функции `cutFill`, что в `geometry.js`, а не переносит округлённый литерал вручную — приведённое число иллюстративно, не более точно, чем сам `EPS_AREA_RATIO`
- Рука: `neutralHand`
```

Формула площади (`erratum-015`, последняя строка) не меняется — только окружающие её строки
возвращены на накопленное состояние. Термин «closure window» этим erratum в исполняемый
вход не возвращается ни разу.

## Патч 2 — `windDirection` как ориентация, не «`u=0` у сердцевины» (поверх `erratum-008`)

**Проблема.** `erratum-008` обосновывает `fromUZero` цитатой спиральной ветки `wind()`
(`geometry.js:1229-1252`, `if (g.winding === 'spiral')`), которую хосомаки/F01 не выполняет
(`winding: 'spiral'` только у `uzumaki`, `catalog.js:183`) — и формулирует правило как
«`uMm = 0` наматывается первым, ближе к сердцевине». `erratum-019` (кольцевая ветка, та,
что реально выполняется на F01) требует обратного: внутреннее `u` на F01 живёт на
`[sRice0, sRice1] ≈ [5,04; 92,4]` мм, и `u = 0` там не встречается вовсе (это внешний хвост
нахлёста, который `erratum-019` прямо запрещает писать в `uAtRayMm`). Оба erratum о разных
вещах внутри себя корректны; вместе — буквальное прочтение `erratum-008` («ищи `u ≈ 0` у
сердцевины») противоречит буквальному прочтению `erratum-019` («на F01 `u = 0` там не
пишется»).

Было (текущий текст, тип `WindDirection`, `erratum-008-wind-direction.md:69-72`):

```ts
// Какой конец диапазона uMm ∈ [0, L] наматывается первым (ближе к сердцевине,
// s = 0 в инварианте 3), а какой — последним (снаружи, ближе к шву).
// 'fromUZero'   — uMm = 0 наматывается первым, uMm = L — последним.
// 'fromULength' — uMm = L наматывается первым, uMm = 0 — последним.
```

Стало:

```ts
// Направление роста параметра листа u вдоль накопленной дуги s (инвариант 3) —
// конвенция координат, не утверждение о том, что конкретное значение u = 0 физически
// присутствует на конкретном fixture. На кольцевой ветке (F01, F02 — не spiral, см.
// Erratum 019) внутреннее пересечение живёт на [sRice0, sRice1] листа, u = 0 туда не
// попадает вовсе (это внешний хвост нахлёста, Erratum 019); u = 0 — участок ближе к
// сердцевине только на спиральной ветке (uzumaki, catalog.js:183).
// 'fromUZero'   — u растёт вместе с накопленной дугой s (малый u — раньше по намотке).
// 'fromULength' — u убывает вместе с накопленной дугой s (малый u — позже по намотке).
```

Было (текущий текст, абзац обоснования, `erratum-008-wind-direction.md:80`):

```markdown
Для F01–F08 используется одно значение — `windDirection: 'fromUZero'` — во всех fixtures, кроме специально предназначенного для проверки переворота F08. Основание для выбора именно этого направления, а не произвольное: `play/model/geometry.js:1229–1252` (legacy `wind()`, цикл `for (let шаг = 0; шаг < KMAX * NB && sп < L; шаг++) { ... }`). Конкретно строка `const r = (k === 0) ? r0e + t0 * (шаг * DPHI) / TAU : top[b];` — для первого витка (`k === 0`) радиус `r` растёт вместе с `шаг` от `r0e` (сердцевина) наружу; и строка `u0[idx] = sп / L` — накопленная длина дуги `sп` монотонно растёт вместе с `шаг` в том же цикле. Значит меньший `sп` (и меньший `u0 = sп / L`) откладывается на меньший радиус — наматывается первым, ближе к сердцевине. `fromUZero` продолжает то же соответствие «малый `u` → внутренний виток», а не изобретает новое — это упрощает сравнение V2 и legacy на шаге 5 плана миграции ADR-001 («расхождение документировать, а не подгонять»). Значение — конвенция, а не физический факт: утверждения владельцем не требует (см. выше), но обязано быть записано здесь, а не только выбрано в коде.
```

Стало:

```markdown
Для F01–F08 используется одно значение — `windDirection: 'fromUZero'` — во всех fixtures, кроме специально предназначенного для проверки переворота F08. Основание для выбора именно этого направления, а не произвольное: `play/model/geometry.js:1229–1252` (legacy `wind()`, спиральная ветка, `uzumaki`) — строка `u0[idx] = sп / L` показывает, что накопленная длина дуги `sп` растёт монотонно вместе с индексом шага. `fromUZero` фиксирует именно это направление роста — `u` растёт вместе с `s` — как конвенцию для ВСЕХ веток `wind()`, не только спиральной: на кольцевой ветке (F01, F02, хосомаки — не spiral, `catalog.js:183`) та же монотонная связь `u ↔ s` верна для внутреннего пересечения на его собственном диапазоне `[sRice0, sRice1]` (Erratum 019), без утверждения, что `u = 0` физически достижимо на этой ветке. Значение — конвенция направления, а не физический факт о положении `u = 0`: утверждения владельцем не требует (см. выше), но обязано быть записано здесь однозначно, а не как «`u = 0` у сердцевины», что верно только для спиральной ветки и вводит в заблуждение на кольцевой.
```

## Патч 3 — интеграл по средней линии: у риса и нори разные `r`, не общий (поверх `erratum-013`, Патч 1)

**Проблема.** `erratum-013` (Патч 1, «Стало» инварианта 1, и Патч 2, строка F01 «Дуга по
слоям») цитирует `geometry.js:1351-1358` как формулу «по средней линии слоя» — но этот
конкретный цикл (проверка «хватило ли листа на оборот нахлёста») вычисляет `r` только для
**нори** (`rЭ = top[b] - W/2`, где `top[b]` — уже готовая внешняя граница НОРИ после
укладки обоих слоёв: `rн` определяется на `geometry.js:1296`, а `top[b] = rн` присваивается
на `geometry.js:1320`). У риса своя средняя линия — `(r0b + rр)/2`, другое вычисление,
другие переменные (`r0b`, `rр` — внутренняя и внешняя граница рисового кольца,
`geometry.js:1294-1295`). Формула `ds = √(r² + dr²) dφ` общая для обоих слоёв; сам
`r` — нет. Разработчик, который скопирует цитируемый код 1:1 «для текущего слоя» без
замены `r`, получит один и тот же радиус нори для расчёта дуги ОБОИХ слоёв — `rice.arcMm`
совпадёт с `nori.arcMm` не потому, что дуги действительно равны, а потому что интегрировал
не тот радиус. Строка F01 «Дуга по слоям (независимо)» это не ловит буквальным своим
текстом: такая реализация самосогласованна (заявленное `arcMm` совпадает с тем же неверно
скопированным интегралом) — и именно ЭТА строка, не только прозаический инвариант 1,
исполняется разработчиком напрямую, так что дыру нужно закрыть в обеих.

### Патч 3а — инвариант 1 (поверх `erratum-013`, Патч 1)

Было (текущий текст, фрагмент `erratum-013`, Патч 1, «Стало» инварианта 1 — без изменений
до и после этого фрагмента):

```markdown
...по средней линии слоя (тот же способ, каким сама намотка уже считает длину листа при закрытии кольца — `play/model/geometry.js:1351-1358`, `const ds = Math.sqrt(r*r + dr*dr) * DPHI`, где `r` — средняя линия текущего слоя, комментарий в коде — «длина листа меряется по его средней линии»)...
```

Стало (текст справа и слева от фрагмента, «, и сверена САМА С СОБОЙ…» и далее, не меняется
— склейка остаётся на том же месте, что и в «Было»):

```markdown
...по средней линии СВОЕГО слоя — формула общая, `r` разный: для нори — тот же способ, каким сама намотка уже считает длину листа при закрытии кольца (`play/model/geometry.js:1351-1358`, `const ds = Math.sqrt(r*r + dr*dr) * DPHI`, где `r = top[b] - W/2`, внешняя граница нори минус половина её толщины, `top[b] = rн` на `geometry.js:1320`); для риса — то же `ds`, но `r = (r0b + rр)/2` (среднее внутренней и внешней границы рисового кольца, `geometry.js:1294-1295`)...
```

Отдельно, в конец того же абзаца инварианта 1 — после «...это следствие геометрии, не
брак.» и перед «Отчёт, где единственное измерение длины…» (текст между ними не меняется) —
добавить одно новое предложение:

```markdown
Цитируемый код `geometry.js:1351-1358` сам по себе строит только нори; повторное использование его `r`-расчёта для риса без замены на `(r0b+rр)/2` даёт один радиус на оба слоя (Erratum 020) — это не реализация данного инварианта, а ровно тот регресс, который таблица F01 обязана ловить.
```

### Патч 3б — приёмка F01, строка «Дуга по слоям (независимо)» (поверх `erratum-013`, Патч 2)

Было (текущее накопленное состояние — `erratum-013`, Патч 2, «Стало»):


## Патч 4 (minor) — асимметрия ядра по всем лучам, не по осям (поверх `erratum-014`)

максимум `r0(φ) = min((Wc/2)/|cosφ|, (Hc/2)/|sinφ|)` по всем лучам: для прямоугольника с
полуосями `a = Wc/2 = 0,5`, `b = Hc/2 = 0,72` эта функция достигает максимума **в углу**

глобальная асимметрия `max − min ≈ 4,38 − 2,5 = 1,88 мм`, не `1,1 мм`. Проверка

любом разумном выборе константы независимо от того, 1,1 или 1,88 — это не блокер, только
неточность иллюстративного числа и, следовательно, гарантии в «Предупреждении».
