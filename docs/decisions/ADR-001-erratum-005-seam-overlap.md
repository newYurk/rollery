# ADR-001, Erratum 005 — окрестность шва получает число: overlapArcRad, а не текстовая оговорка

- **Статус:** proposed — черновик по итогам adversarial review ветки `architecture/core-v2-foundation`, закрывает blocker `seam-neighbourhood-free-parameter` (пережил 1/2 skeptics, `docs/handoff/core-v2-validation-findings.md:264-283`).
- **Это не решение владельца.** В отличие от Erratum 002/003, здесь нечего решать ценностно: величина нахлёста нори — геометрическое следствие уже принятых инвариантов 1–4 ADR-001 (единая длина листа, полнота координат, параметризация по дуге, явный шов) и уже сделанного выбора «нори нерастяжима». Правка инженерная: она называет числом то, что контракт уже подразумевал текстом.
- **Заменяет в `core-v2-fixtures.md`:** тип `seam` в `FixtureReport`, строку приёмки «Нори по лучу» в F01, добавляет одну строку в таблицу mutation tests.
- **Кому:** разработчику/ревьюеру Core V2.

## Проблема

`core-v2-fixtures.md:81` требует: «Ровно одно пересечение на всех лучах, кроме явно выделенной угловой окрестности шва» — но нигде не говорит, СКОЛЬКО лучей входит в эту окрестность. Тип отчёта тоже не даёт зацепиться:

```ts
seam?: { uStartMm: number; uEndMm: number; angleRad: number }
```

`uStartMm/uEndMm` — координата ЛИСТА, `angleRad` — один угол на РОЛЛЕ, без ширины и без формулы, которая связывает одно с другим. Инвариант 4 ADR-001 требует «конкретный диапазон координат листа И положение в ролле» — сейчас есть только половина каждого из двух диапазонов.

**Контрпример** (`core-v2-validation-findings.md:270`, источник — живой расчёт нахлёста хосомаки, `play/model/geometry.js:1376-1378` и эталон `play/checks.js:139`): на входе F01 (лист 105 мм, `hoso: { d: 28.9, turns: 1.19 }`) нахлёст обязателен по построению — `Lbare = 17,64 мм` при среднем радиусе намотки `Rср ≈ 14,53 мм` даёт `φ_нахл = Lbare/Rср ≈ 1,215 рад ≈ 69,6°`, то есть **~19 % лучей** (270 из 1440 в легаси-разбиении) несут два слоя нори, а не одна «окрестность у шва» шириной в один бин. Реализация, которая честно возвращает эти ~19 % двоек, и реализация, которая наматывает лист дважды по всей окружности, обе проходят нынешнюю формулировку F01 — потому что формулировка не считает.

Легаси-числа (`d=28.9`, `turns=1.19`, `Lbare=17.64`) — не истина для V2 (правило зафиксировано в `core-v2-fixtures.md`, раздел «Правила fixtures»): они здесь только как ориентир масштаба и как перекрёстная проверка формулы, не как обязательный numeric oracle.

## Решение — разделить тип `seam`

### Патч в `core-v2-fixtures.md`, блок `FixtureReport`

**Было:**

```ts
seam?: { uStartMm: number; uEndMm: number; angleRad: number }
```

**Стало:**

```ts
seam?: {
  // координата ЛИСТА — куда на исходном полотне попадает нахлёстывающий хвост.
  // Инвариант 3: это конец обычной u-параметризации по дуге, не отдельная шкала.
  uStartMm: number
  uEndMm: number

  // угловой сектор РОЛЛА, где нори лежит ДВУМЯ слоями. Инвариант 4: явный
  // диапазон, не выводится из числа витков задним числом.
  angleStartRad: number
  angleEndRad: number        // (angleEndRad - angleStartRad) mod 2π = overlapArcRad

  // одна и та же физическая величина в двух единицах — держать оба поля,
  // чтобы связь между листом и роллом была проверяемой, а не подразумеваемой
  overlapMm: number          // длина нахлёстывающего хвоста нори, в мм листа
  overlapArcRad: number      // тот же нахлёст в угловой мере ролла, рад

  // измеренный результат намотки, а не вход puzzle-уровня (инвариант 6)
  turnsMeasured: number      // = 1 + overlapArcRad / (2π) для одного полного витка + нахлёст;
                              // для случая, когда лист не замкнул кольцо (`turnsMeasured < 1`),
                              // считается тем же способом, каким kernel вообще меряет пройденный угол
}
```

**Обязательная перекрёстная проверка** (это и есть «явная связь», которой не хватало): нахлёст, посчитанный по листу, и нахлёст, посчитанный по ролу, обязаны сходиться —

```
| overlapMm − overlapArcRad · Rср | ≤ EPS_LENGTH_MM
```

где `Rср` — средний радиус намотки в зоне нахлёста (тот же смысл, что `roll.diameterMinMm/diameterMaxMm` уже дают отчёту — если оба диаметра совпадают в пределах допуска, `Rср = (diameterMinMm + diameterMaxMm)/4`; если нет, зона нахлёста обязана попасть в свой собственный под-диапазон радиуса, и это отдельная диагностика, не молчаливое усреднение). Реализация, которая рассинхронизирует `uEndMm−uStartMm` и `overlapArcRad`, ловится этой строкой раньше, чем строкой про лучи ниже.

### Новая константа `EPS_RAY_FRACTION`

По тому же образцу, что и `EPS_LENGTH_MM` (`core-v2-fixtures.md:54`, «обоснованной разрешением дискретизации»):

> Численный допуск для доли лучей задаётся константой `EPS_RAY_FRACTION`, обоснованной числом лучей `RAY_COUNT`, которым kernel строит `wrapIntersectionsByRay`. Минимальная содержательная величина — один луч: `EPS_RAY_FRACTION ≥ 1 / RAY_COUNT`. И `RAY_COUNT`, и производный от него `EPS_RAY_FRACTION` — свободные параметры реализации (тот же статус, что уже разрешён для `EPS_LENGTH_MM` в `docs/handoff/core-v2-developer-brief.md:108`): разработчик выбирает число и документирует его в PR-заметке. Обязательное условие валидности выбора: `overlapArcRad / 2π` (ожидаемая доля двухслойных лучей) обязана быть заметно больше `EPS_RAY_FRACTION` — иначе строка приёмки ничего не проверяет. Для F01 (`overlapArcRad/2π ≈ 0,19`) годится почти любой разумный `RAY_COUNT` начиная с нескольких десятков; легаси использовал 1440 лучей (`geometry.js`, `NB`) — это не требование к V2, только прецедент выбора.

## Патч в `core-v2-fixtures.md`, таблица приёмки F01

**Было** (строки «Шов» и «Нори по лучу», `core-v2-fixtures.md:80-81`):

| Инвариант | Ожидание |
|---|---|
| Шов | Существует и находится на листе |
| Нори по лучу | Ровно одно пересечение на всех лучах, кроме явно выделенной угловой окрестности шва |

**Стало** — разбито на два независимых утверждения, потому что это два разных инварианта, а не один:

| Инвариант | Ожидание |
|---|---|
| Полнота координат листа (инвариант 2) | Каждая координата листа `uMm ∈ [uMinMm, uMaxMm]` отображается ровно один раз в намотку — это утверждение о листе, не о лучах ролла, и не имеет исключений у шва |
| Явный шов (инвариант 4) | `seam` присутствует; `seam.uStartMm/uEndMm` внутри листа; `seam.angleStartRad/angleEndRad` внутри `[0, 2π)`; `|overlapMm − overlapArcRad·Rср| ≤ EPS_LENGTH_MM` |
| Нахлёст нори по лучам ролла (физика намотки, отдельно от полноты листа) | Доля лучей `roll.wrapIntersectionsByRay`, показывающих ровно одно пересечение, `= 1 − overlapArcRad/2π`, допуск `±EPS_RAY_FRACTION`. Симметрично: доля лучей с ровно двумя пересечениями `= overlapArcRad/2π ± EPS_RAY_FRACTION`. Лучей с 0 или ≥3 пересечениями быть не должно (это уже покрыто «полнотой координат» выше, но проверяется здесь как честный отказ, если модель дала мусор) |
| Ориентир масштаба (не обязателен к точному совпадению, только к порядку величины) | Для входа F01 (`лист 105 мм`, стандартная рисовая постель хосомаки) легаси даёт `overlapArcRad ≈ 1,215 рад` (`≈69,6°`, `≈19 %` лучей), `turnsMeasured ≈ 1,19` — `play/checks.js:139`, `play/model/geometry.js:1376-1378`. Несовпадение с этим числом не проваливает F01 само по себе; проваливает нарушение формул выше |

## Что это закрывает

Blocker `seam-neighbourhood-free-parameter` (`docs/handoff/core-v2-validation-findings.md:264`): «окрестность шва — свободный параметр реализации» — больше не свободный: у неё есть имя (`overlapArcRad`), формула (`= angleEndRad − angleStartRad`), источник для сверки порядка величины (`checks.js:139`) и проверяемая связь с координатой листа. Implementation A (честные ~19% двоек) и Implementation B (двойная намотка по всей окружности) из контрпримера теперь различимы: у B `overlapArcRad` либо не может быть меньше `2π` при этом входе, либо расходится с `overlapMm` — обе строки красные.

Косвенно закрывает часть класса «полнота листа vs физика ролла смешаны в одной строке» — F01 теперь проверяет их раздельно, что снижает шанс, что будущая F03-F06 unintentionally скопирует ту же путаницу.

## Что НЕ закрывает

- Не решает и не трогает зарезервированную развилку («растягивается ли КУСОК начинки вместе с изгибающимся листом, или лист несёт дугу отдельно, а кусок хранит форму и площадь и проскальзывает») — F01 пустой, кусков начинки в нём нет, развилка к геометрии самой нори не относится.
- Не решает #165 («от чего считать угол: от дуги нори или от длины риса») — это вопрос про РИС, у пустого F01 патчей и заполненной рисовой раскладки, о которой спорит #165, тоже нет; `angleStartRad/angleEndRad` здесь считаются от дуги нори (она нерастяжима — это уже принятый, не спорный инвариант), не от риса.
- Не даёт формулу вычисления `Rср` для случаев, где `roll.diameterMinMm ≠ roll.diameterMaxMm` за пределами допуска (некруглый ролл) — оставлено разработчику как отдельная диагностика, не молчаливое усреднение (см. текст перекрёстной проверки выше).
